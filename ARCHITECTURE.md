# Форман — устройство приложения

Помощник бригадира HVAC (Сан-Диего). Один код на Expo для iPhone, Android и веба.
Интерфейс на русском; английский и испанский подключаются позже через словарь.

## Структура

    +html.tsx               HTML-обёртка веб-версии (lang="ru", ссылка команды)

## Рабочая версия (5 функций, 23.11.2026)

Нижняя панель — только «Работы» и «Ещё». Обучение, библиотека установок, законы и склад открываются из «Ещё»
экранами поверх вкладок (`src/app/ref/*`), их код не тронут. Экран объекта (`jobs/job-screen.tsx`):
1. Объект — название, адрес (`Job.address`), № заказа.
2. Заказ — скрин заказа и «Разобрать» (как было).
3. Трак (`jobs/truck-section.tsx`) — «✓ Всё загружено» (`markAllLoaded`: всё неотмеченное → «есть», в траке = нужно;
   «Нет» и вписанное руками не трогает), дальше «Есть / Нет» у строки; подробная карточка — по нажатию на название.
4. Фото по шагам (`jobs/steps-section.tsx`, `PHOTO_STEPS` в jobs-model.ts) — 8 шагов, фото помнит шаг (`JobPhoto.step`).
5. Сюрприз (`jobs/surprise-section.tsx`, `Job.surprises`) — текст + фото → «Отправить в офис» (Web Share), отметка «отправлено».
Сдать и отчёт — пробелы видны, ничего не блокируют. Отчёт — `buildFieldReport` (jobs-model.ts), язык EN/RU
переключается кнопкой, по умолчанию английский, выбор хранится на телефоне (`fm.reportLang`).
Этапы-галочки и «Бригада» убраны с экрана; их данные в документе «Работы» остаются. В копию файлом входят шаг фото и
сюрпризы (`parseBackup` получает `isStep` и `surprises`). Проверки: `npm run test:field`, `tests/smoke-web.mjs`.

## Синхронизация

- **Команда** = ID команды + секретный код (личных входов пока нет). Код вводится во вкладке
  «Ещё»: ссылка `…#s=<команда>&k=<код>` или «ID код» через пробел. Проверка — функцией базы `space_info`.
- **Сначала устройство.** `saveDoc / deleteDoc` всегда сразу пишут на устройство и помечают запись
  «не отправлено». Если команда подключена — тут же отправляют в базу. Нет связи — данные остаются на
  устройстве и уходят позже: при возврате в приложение, при появлении сети (веб) и раз в 30 секунд.
- **Чтение.** `getDoc / listDocs` при связи берут свежие данные из базы, но неотправленные локальные
  правки важнее. Без связи — локальная копия.
- **База.** Только функции Supabase (RPC) по HTTPS: `space_info, doc_list, doc_get, doc_set,
  doc_delete`; каждая сама проверяет код команды. Коллекции «Формана» в базе имеют префикс `fm_`
  (например `fm_shift`), чтобы не смешиваться с коллекциями «Склада» той же команды.
- **Статус** (строка под формами): только на устройстве / синхронизация / синхронизировано /
  не отправлено N / нет связи / неверный код. Функции синхронизации никогда не бросают ошибку в экран.
- **Склад.** Вкладка «Склад» открывает https://sorvingbel-hue.github.io/fixpro-sklad-app/ ; если команда
  подключена, — сразу на этой команде (код передаётся после `#`, на сервер страницы не уходит).
- Телефон и веб-версия работают с **одной и той же базой**: одна команда видит одни и те же данные.

## Настройка

Адрес и публичный ключ базы — в файле `.env` (в git не попадает, образец — `.env.example`):

```
EXPO_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
EXPO_PUBLIC_SUPABASE_KEY=sb_publishable_...
```

## Запуск на телефоне (Expo Go)

1. Установить Expo Go из App Store / Google Play.
2. На компьютере: `npm install`, затем `npx expo start`.
3. iPhone: навести камеру на QR-код в терминале. Android: отсканировать QR в Expo Go.
   Если телефон в другой сети: `npx expo start --tunnel`.

## Веб-версия

- Разработка: `npm run web`.
- Сборка для тестеров: `npm run web:export` → папка `dist/` (статичные страницы). Её можно выложить на
  любой статический хостинг (GitHub Pages, Netlify). Для адреса в подпапке (например `/forman/`)
  добавить в `app.json` → `expo.experiments.baseUrl`.
- Ссылка `https://<сайт>/#s=<команда>&k=<код>` сразу подключает тестера к команде; код убирается
  из адресной строки.

## Копия файлом и второй телефон (М7)

- Объекты и фото живут только на телефоне (localStorage `fm.jobs.v1`, `fm.job.<id>.work`; фото — IndexedDB
  `forman-photos`/`blobs`, ключи `<id>:full` и `<id>:thumb`). Чтобы они не пропали и чтобы перенести их на второй
  телефон — карточка «Копия и второй телефон» в списке объектов.
- «Сохранить копию (файл)» → `forman-kopiya-ГГГГ-ММ-ДД-ЧЧММ.forman.json`:
  `{kind:'forman-backup', v:1, createdAt, app:'forman', jobs, works:{[jobId]:WorkV03Doc}, photos:{[photoId]:dataURL JPEG}}`.
  Пример (ДЕМО) в копию не входит. Если браузер умеет `navigator.canShare({files})` — кнопка «Отправить копию»
  (AirDrop, WhatsApp, «Файлы»), иначе файл скачивается. Время копии — `fm.backup.last`; если есть объекты,
  а копии нет или ей больше 3 дней — в карточке «Сделайте копию».
- После скачивания «Формана» не знает, сохранил ли человек файл (в Safari есть «Отмена»), поэтому дата копии
  записывается только после нажатия «Файл сохранён». После «Отправить копию» — сразу (меню «Поделиться» завершилось).
- «Загрузить копию» строго проверяет файл (`parseBackup`): kind/v; объект — id из простых символов, настоящая дата
  создания, тексты не длиннее пределов (`FILE_LIMITS`, длинное обрезается), у фото — простые id и числа;
  «Работа» — `sanitizeWork` (work-model.ts): только документ этого объекта, позиции/вопросы без id или не объекты
  отбрасываются, недостающие поля — пустые; фото — только data:image JPEG/PNG/WebP. Файл больше 150 МБ не читается.
  Даты из будущего: если копия «из будущего» (часы того телефона спешат), все её даты сдвигаются назад на эту
  разницу, ни одна дата не позже «сейчас», датам такого файла не верим (см. ниже) и показываем предупреждение.
- Слияние (`planMerge`) — по частям объекта, у каждой своё время правки, чтобы правки с двух телефонов не затирали
  друг друга:
  - поля (название, № заказа, заметка и незнакомые поля новых версий) — более свежие по `editedAt`
    (его ставит `patchJob`; у старых записей — `updatedAt`);
  - фото — объединяются; id удалённых фото хранятся в `removedPhotos` (до 200), такие фото не возвращаются
    и стираются на другом телефоне; фото с id чужого фото этого телефона пропускаются. Больше 60 фото после
    слияния — ничего не выбрасывается, человек получает предупреждение;
  - «Работа» (`mergeWork`) — более свежий по `updated` документ главный, позиции и вопросы, которых в нём нет,
    добавляются, пустые поля позиции заполняются из другого, отметки этапов объединяются, заметки — обе;
  - если часы телефона с копией спешат — при расхождении остаётся своё, новое из файла добавляется.
  Сравнивается содержимое, а не даты: повторная загрузка того же файла и обмен копиями туда-обратно ничего не меняют.
- Порядок записи (`restoreBackup`): фото в IndexedDB (долго — на экране «Загружаю фото: N из M», список объектов
  в это время не открывается и не меняется) → план слияния заново по свежим данным телефона → «Работа» → список.
  Если запись не поместилась — всё записанное возвращается как было, фото этой загрузки стираются:
  «ничего не изменено». Итог: «Загружено: N объектов, M фото; пропущено: K» и пояснения.
- `normalizeJobs` и `normalizeWork` сохраняют незнакомые поля: старая версия, сохраняя объект, не стирает поля,
  которые добавила новая. Экран объекта обёрнут в `JobGuard`: если данные объекта всё же испорчены — вместо белого
  экрана «Объект не открылся», «Все объекты» и «Удалить этот объект».

## Разбор скрина заказа (М8, распознавание на телефоне)

- Скрин заказа → «🔎 Разобрать» → распознавание В БРАУЗЕРЕ ТЕЛЕФОНА (tesseract.js 7.0.0, WebAssembly, Web Worker) →
  черновик позиций → бригадир правит/удаляет/добавляет строки → «Подтвердить и добавить в сверку» (или «Отмена»).
  Скрин никуда не отправляется: картинка берётся из IndexedDB и распознаётся здесь же; ключей, облака, покупок нет.
  Обычные фото остаются вложениями и не распознаются. Ручной ввод в «3. Сверка» — как был.
- Путь (правка dot): в «2. Фото и скрин заказа» две разные кнопки — «📷 Фото объекта — просто вложение» (телефон
  предложит снять или выбрать из галереи) и «🧾 Скрин заказа — можно разобрать». Добавили не той кнопкой — «⇄» под
  миниатюрой или в крупном просмотре переносит фото ↔ скрин заказа (`setPhotoKind`; пример скрина не переносится).
  Черновик: сверху исходный скрин (миниатюра → нажать → крупно во всю ширину, у скрина заказа — копия `:ocr`);
  спорные строки (флаг, «уже есть в сверке», второй раз на скрине) — первыми и раскрыты; уверенные — свёрнутым
  списком «Ещё N строк без вопросов» (коротко «• название — кол-во»; раскрыть — и править). Группы решаются один раз
  при разборе, строки не прыгают во время правки. Числа отдельно от названий (фото экрана под углом: строки
  распались, `orphanNumbers` ≥ 2) — оранжевое предупреждение: эти количества не взяты, допишите или сделайте скриншот.
- Файлы распознавания — на своём сайте, без CDN: `public/ocr/t7/` (`tesseract.min.js`, `worker.min.js`,
  `tesseract-core-simd-lstm.wasm.js` — Safari 16.4+/Chrome, `tesseract-core-lstm.wasm.js` — без SIMD,
  `eng.traineddata.gz` — модель 4.0.0_best_int из `@tesseract.js-data/eng@1.0.0`, sha256 проверяет `npm run ocr:assets`).
  На сервере 10,6 МБ, телефон скачивает ≈7 МБ (≈4,6 МБ по сети со сжатием). В общий офлайн-кэш (≈3,9 МБ) НЕ входят —
  это утроило бы первое открытие для всех. Грузятся при первом «Разобрать» (на экране написано: «до 7 МБ»), service
  worker кладёт их в отдельный кэш `forman-ocr-files`, который переживает обновления «Формана»; дальше разбор работает
  без сети (на экране: «✓ Модуль распознавания сохранён на этом телефоне»). У каждого файла `ocr/**` в `sw.js` записан
  хэш содержимого (`OCR_FILES`, подставляет `sw-stamp`): в кэш кладётся файл только с этим хэшем (скачан мимо HTTP-кэша,
  хэш проверяется в service worker); файл поменялся на сайте — новая сборка, и при её включении из кэша удаляется
  только он (остальные 7 МБ заново не качаются). Если первый разбор прошёл мимо service worker (первое открытие по
  медленной сети: он ещё ставился), страница после удачного разбора ждёт его включения и просит сохранить файлы
  (`OCR_KEEP`). tesseract.js не входит в код приложения: `tesseract.min.js` подключается `<script>` при первом разборе.
  Модель в IndexedDB не дублируется (`cacheMethod: 'none'`). После обновления tesseract.js: `npm run ocr:assets`
  (папка `t7` = 7.x; новая major-версия — новая папка, хэши подставятся сами).
- Что распознаётся: у скрина заказа при добавлении, кроме полной копии (1600 px по длинной стороне) и миниатюры,
  пишется копия для распознавания `<id>:ocr` — ширина как у скрина (до 1600 px), длина какая есть, до 12 Мп, JPEG 0.9.
  Длинный скрин прокруткой 1170×4960 «по длинной стороне» стал бы 377×1600 — из 40 позиций читалось 5; с копией — 40.
  У скринов, добавленных раньше или восстановленных из копии файлом (там только полная), перед распознаванием
  картинка увеличивается до ширины 1000 px (`upscaleFactor`, не больше ×3 и 12 Мп) — тот же скрин тоже 40 из 40.
  В копию файлом `:ocr` не входит; удаляется вместе с фото.
- `order-parse.ts` (формат №1 — список позиций с количеством: «Qty: 6», «Qty 6», «Qty 2.00», «x6», «6 x», «2.00 x $35.00»,
  «6 ea», «6 pcs», число в колонке «Qty»; «Qty» на строке ниже названия): строки собираются из слов по положению на
  скрине (`groupWordsToLines`), итоги/цены/телефоны/адреса/шапка отбрасываются (видны в «Пропущенные строки»).
  «Flex duct 8» / «Qty 12» — количество 12 из «Qty», «8» остаётся в названии. НЕ УГАДЫВАТЬ → `qty: null`, оранжевое
  «проверь количество», поле пустое, под строкой — почему:
  - цифра неуверенная (уверенность < 70 — по слову и по знакам-цифрам; для «x4», «6ea», «Qty:6» — по знакам), буква
    вместо цифры (O/0, l/1/I, S/5, B/8, Z/2), ноль, > 999, «Qty» без цифры;
  - цифра шире, чем бывает одна цифра этого шрифта на этом скрине (`digitRef`/`digitTooWide`: «11», прочитанное как «1»
    с уверенностью 98, — рамка знака вдвое шире обычной «1»; эталон — типичная ширина цифр того же скрина);
  - голое число в конце строки («Filter MERV 13», «Breaker 2 pole 30») — количество ТОЛЬКО при доказательстве:
    (а) явный маркер в строке или строкой ниже («Qty 2», «Qty: 2», «x2», «2 ea/pcs/ft»); (б) выше на скрине есть
    заголовок колонки количества («Qty», «Quantity», «Кол-во»; в строке заголовка только слова шапки — «Description
    Qty Price Total» тоже заголовок, а не итог) и число стоит в этой колонке по горизонтали (рамки слов, допуск —
    высота строки); (в) число выровнено по краю с уже доказанным числом соседней строки (до 3 строк) под тем же
    заголовком — колонка, «уезжающая» вбок на фото с перекосом. Без рамок слов (только текст; в приложении рамки
    есть всегда) — заголовок вида «Description Qty» («Qty» последним) и строки не преимущественно с явным «Qty».
    Без доказательства: число остаётся в названии, `qty: null`, флаг, причина «число в конце может быть частью
    названия — проверь» (`TRAIL_NOTE`). В колонке «Qty» короткое «слово» вместо числа («3» прочитано как «a») — тоже
    позиция с пустым количеством и флагом (`COL_NOTE`), а не потерянная строка.
- До «Подтвердить» сверка не меняется (черновик только в памяти экрана; «← Все объекты» при открытом черновике
  спрашивает). Подтверждение (`addOrderItems`): заказано = нужно = кол-во, «в траке» пусто, «не проверял», источник
  «скрин заказа»; без количества — добавляется пустым; строки со стёртым названием не добавляются (сказано в сообщении).
  Повторы по названию (`planConfirm`/`findExisting`, без учёта регистра и знаков): строка, которая уже есть в сверке
  (повторный разбор того же скрина, второй перекрывающийся скрин того же заказа), показывается в черновике «Уже есть
  в сверке: «…» — заказано 8, в траке 4. Что сделать?» с выбором «Оставить как есть» (по умолчанию) / «Заменить
  количество: 8 → 6» (`setOrderQty`: заказано = нужно = новое, «в траке» не трогается) / «Добавить отдельной
  позицией»; второй раз на одном скрине — «Не добавлять второй раз» (по умолчанию) / «Добавить отдельно». Молча не
  задваивается ничего; над кнопкой «Подтвердить» — что именно произойдёт.
  Второе нажатие «Разобрать», пока идёт разбор, не начинает новый; результат остановленного разбора на экран не попадает.
- «6. Итог» → «Недостача по заказу» (`shortages` по существующему `verdict`): «<позиция>: заказано 6, в траке 4 — не хватает
  2 шт.»; то же — в отчёте .txt («НЕДОСТАЧА ПО ЗАКАЗУ»).
- «🧪 Попробовать разбор на примере»: вымышленный `ocr/primer-zakaza.png` (1170×2000, «ORDER #DEMO-OCR (sample)», 6 позиций,
  у «Condensate pump» цифра размазана) добавляется в объект как скрин заказа с пометкой «ПРИМЕР» (один раз; повторное
  нажатие разбирает уже добавленный) и сразу распознаётся тем же путём, что настоящий скрин (никакого подставленного
  текста). Пример — не настоящий заказ: не закрывает шаг «Фото и заказ», не гасит «Нет скрина заказа», в отчёте
  отдельной строкой; позиции с него в сверке — источник «скрин заказа (ПРИМЕР, вымышленный)», в недостаче — «[ПРИМЕР]».
- Честность: модуль не скачался / нет сети в первый раз / ошибка / нет текста → понятное сообщение и «впишите вручную»;
  «Остановить» во время загрузки или распознавания. В приложении Expo Go распознавания нет — так и написано.

## Без сети (service worker, только веб-сборка)

- `public/sw.js` попадает в `dist/sw.js`; `npm run web:export` после `expo export` запускает `scripts/sw-stamp.mjs`,
  который подставляет версию (хэш файлов сборки) и список файлов для кэша (страницы вкладок, `_expo/static`, `assets`,
  иконки, manifest — ≈4 МБ). Без этого шага новая сборка не будет замечена как обновление — публиковать только
  результат `npm run web:export`.
- Регистрация — в `src/lib/sw-update.ts` (из корневого `_layout` через `UpdateBanner`): только веб и только
  продакшен-сборка; в разработке (`__DEV__`) SW не ставится, а оставшийся — снимается. Scope — `/fixpro-sklad-app/forman/`.
- Главное правило: на телефоне всегда ОДНА версия целиком — и страницы, и код из кэша `forman-sw-<версия>`
  (сначала кэш). Новую сборку браузер замечает по новому `sw.js` (проверка мимо HTTP-кэша при каждом открытии,
  при возврате в приложение и раз в 30 минут), скачивает целиком в новый кэш (не скачался хоть один файл —
  установка не удалась, неполный кэш удаляется) и ждёт: «Есть обновление — нажмите, чтобы обновить» →
  `SKIP_WAITING` → перезагрузка; или новая версия включается сама, когда «Форман» полностью закрыли и открыли.
  Так не бывает «страница новой сборки, код старой» (белый экран без сети при переходе на вкладку) и «то новая,
  то старая версия» (старый код переписал бы данные новой). При включении новой версии старые кэши `forman-sw-*`
  удаляются; другие открытые вкладки со старым кодом сами перезагружаются через ~1 с.
- Страница, которой нет в сборке (незнакомый адрес), — из сети, в кэш не кладётся; без сети — главная.
  Ключи кэша — без `?query`. Запросы вне папки «Формана» («Склад»), к другим сайтам (`*.supabase.co`) и не-GET
  SW не трогает. Если `sw.js` не прошёл через `sw-stamp` (метка версии на месте) — SW ничего не кэширует.
- Данные на телефоне (localStorage, IndexedDB) обновление не трогает.
- Аварийно выключить SW: выложить вместо `sw.js` файл из шапки `public/sw.js` (в `install` — `skipWaiting()`,
  в `activate` — удалить кэши `forman-sw-*`, `self.registration.unregister()` и перезагрузить вкладки).
